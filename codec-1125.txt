# Що екстрактувати першим

Не тягни всю гру одразу. Витягни 5-7 цільових прикладів — це закриє 80% pattern-recognition. Список:

**Traits як референси:**
- trait_Creative.xml — найближче до Неспокійний Мрійник по характеру
- trait_Genius.xml — структура Focused-схильного трейта
- trait_Bookworm.xml — простий hobby trait, чисте посилання
- trait_Loner.xml — приклад negative-tendency trait зі social fatigue логікою

**Buffs:**
- Будь-який buff_Inspired_* — як EA реалізує Inspired moodlet
- buff_Tense_FromOverwhelmed (або аналог) — accumulation pattern
- buff_Reward_TraitName_* — як працюють reward traits з aspirations

**Aspirations:**
- aspiration_Author_BestsellingAuthor.xml (Writer track) — найближча структура до твоєї Знайти Себе
- aspiration_Knowledge_RenaissanceSim.xml — multi-skill tracking, бо у тебе теж generic skill objective
- Один з milestones окремо щоб побачити як objective→milestone тримаються разом

**Rabbit-hole career:**
- career_Adult_Writer.xml (повна) + careerLevel_Writer_*.xml (декілька рівнів) + careerTrack_Writer_*.xml (branches) — це твій шаблон для Незалежного Творця
- career_Adult_Business.xml — більш формальний rabbit-hole патерн

**Self interaction з rabbit-hole/timed outcome:**
- superInteraction_Sim_GoJogging (або як точно називається) — найближче до твоєї "Піти шукати натхнення" по структурі
- superInteraction_Phone_RequestService_* — pattern для phone-initiated rabbit-hole (для майбутньої phone-версії)

**Hidden commodities:**
- Будь-який commodity_Hidden_* де є threshold-based buff triggers — шаблон для Restlessness

# Stop rule для research phase

Codex написав про research stop rule — добре. Конкретизую: **research зупиняється коли можеш своїми словами відповісти на 5 питань, без гуглення і без re-extraction.**

1. Як EA пов'язує trait з buff-on-addition і buff-on-trigger?
2. Як EA реалізує threshold-buff на hidden commodity (приклад з номерами)?
3. Як виглядає objective що тригериться buff'ом vs skill level vs interaction count?
4. Що в .xml career level і чим level 3 відрізняється від level 4 структурно?
5. Як rabbit-hole interaction повертає сіма з outcome — який exact tag/element відповідає за payload moodlet?

Якщо на ці 5 питань відповідаєш — research closed, можна писати власні tunings.

# Engineering decision який варто прийняти зараз

З того що Codex написав і твоїх змін — у вас залишається відкритим питання **pure tuning vs Python script**. Я б ставив це до Milestone 1 явно: подивися на commodity_advertisement і commodity_decay патерни в base game. Якщо EA робить decay і threshold-triggers повністю в tuning без скрипту — pure tuning ОК. Якщо в decompiled core scripts знаходиш Python який реально слідкує за commodity тіками — тоді Python шар треба передбачити з самого старту.

**Перевіряється швидко:** витягни commodity_Bladder (потреба в туалет) — це базовий приклад decaying commodity. Якщо там все в XML і немає Python supporting layer — ти бачиш що pure tuning тягне такі речі. Якщо є Python — отримуєш чесну відповідь що скрипт неминучий для твоєї системи.

# Що я можу зробити прямо зараз

# По 5 пунктах

**1. Extraction scope — погоджено.**
Extract All як snapshot + annotated subset. Додам тільки: snapshot тримати read-only (chmod або просто convention), annotated — окрема папка з копіями. Це запобігає випадковому забрудненню raw reference коли працюєш з прикладами.

**2. Aspiration category mapping — переважно погоджено, з двома уточненнями.**

Знайти Себе → Knowledge ✓
Запалити Іскру → Creativity ✓
Збудувати Шлях → Fortune ✓ (Fortune кращий за Knowledge тут — кар'єрний прогрес фінансово завершується, це fits)

Бути Опорою → Family — рекомендую Family, не Popularity. Popularity в base game tilted на "багато друзів/відомий", тон мерзенно-конкурентний. Family покриває і кровну родину, і "обрану родину" (близькі друзі, сусіди). Для "опорна персона" концептуально точніше. Якщо хочеш не-родинний акцент — тоді Popularity, але переглянь tone descriptions щоб не вийшов "впливова людина" замість "надійна".

Жити Усвідомлено → Knowledge — погоджуюсь з застереженням. Knowledge базово про intellectual pursuit (Renaissance Sim, Computer Whiz). "Усвідомлене життя" це не про знання — це про balance/mindfulness. Категорії яка точно fits в base game нема. Варіанти: (а) лишити Knowledge і зробити tone descriptions які перетягують категорію в бік "self-knowledge", (б) перенести в Family (там Super Parent — вже є nurture-теми). Я б ставив на (а), бо Family вже зайнята "Бути Опорою".

**3. Pure tuning gate — погоджено, додам уточнення критерію.**

Гейт як ти сформулював правильний. Додам один operational test: **MVP лишається tuning-only якщо Restlessness повністю виражається через commodity з:**
- decay rate (XML)
- 3-4 threshold zones (XML)
- buff_add на entry в zone (XML loot)
- buff_remove на exit з zone (XML loot)
- зміни значення тільки через interaction outcomes або periodic decay (XML)

**Python потрібен якщо:** треба cross-sim queries (типу "перевіряй Restlessness усіх членів household") АБО conditional logic складніша за один test type АБО timer не прив'язаний до tick decay (типу "якщо за останні 24 sim hours було X — тоді Y").

Я думаю pure tuning тягне MVP. Складність почнеться на milestone 3-4 коли ти додаси cross-trait interactions і shared states (Burnout який накопичується від кар'єрних дій + recovery через social buffs одночасно). Тоді скриптовий шар майже неминучий.

**4. Tone — погоджуюсь зі змішаним.**

Неспокійний Мрійник лишаємо. Trait names tone OK — це описи характерів, серйозний регістр там доречний.

Reward traits варто переглянути. Внутрішній Стержень дійсно self-help-ish. Альтернативи в Maxis-like регістрі:
- Внутрішній Стержень → Своя Лінія (натяк що сім має власний шлях, без пафосу)
- Ясний Ритм → У Своєму Темпі (більш розмовно)
- Надійна Присутність → Той Хто Поряд (тепліше, менш формально)
- Невгасимий → Невгомонний (Maxis-like, легше)
- Стійкий Прогрес → Без Зривів (іронічніше, Sims-y)

Це пропозиції — обери що звучить, або викоти власні. Ціль — щоб після перемоги aspiration сім отримував trait назва якого не звучить як цитата з мотиваційного блогу.

Aspiration names залишити серйозні (Знайти Себе, Бути Опорою) — тут пафос виправданий бо це life goals. Reward traits — що сім носить щодня — мають бути приземленіші.

Buff/moodlet tone теж переважно OK у твоєму списку. Спалах Ідеї, Тепла Розмова, Маленька Перемога — це Maxis. Моральний Осад, На Межі Вигорання — на грані, але виправдані тим що описують справді негативні моменти. Порожній Успіх — гарно, лишити.

# Codex, по статусу

Прийняв. Scaffold виглядає правильно — README + два CSV + manifest + один pattern doc стартовий мінімум. Решта patterns/*.md нехай заповнюються поступово під час annotation, не блокувати створенням порожніх файлів.

Кілька технічних деталей до practical extraction step щоб уникнути ловушок:

**SHA-256 manifest.** Не хешуй сам .package файли гри — вони мерджаться/ремерджаться при патчах непередбачувано. Хешуй **витягнуті XML** у extracted/. Тоді diff після патчу показує реальні зміни tuning, а не зміни упаковки. Колонки manifest достатньо: relative_path, sha256, file_size, extracted_date, game_version.

**Read-only convention для extracted/.** На Windows це attrib +R на папку рекурсивно або просто git-hook що відкочує зміни. У read-only через chmod на Windows менш зручно. Микита на Win10 — простіше через convention + git pre-commit hook.

**5-7 annotated examples — порядок витягування.** Рекомендую починати з найпростішого до найскладнішого щоб patterns/*.md заповнювалися інкрементально:

1. buff_* (найпростіша структура — 30 хвилин на anatomy)
2. commodity_Motive_* (ключове для tuning gate decision)
3. trait_Creative (зв'язок trait → buff)
4. superInteraction_GoJogging (rabbit-hole pattern)
5. aspiration_BestsellingAuthor + objectives (composite)
6. career_Adult_Writer + levels + branches (найбільший — на кінець)

На третьому файлі вже стає видно повторюваний XML контейнерний скелет (<I c="..." i="..." m="..." n="..." s="...">) і tuning gate decision можна закрити.

**Tuning gate test — конкретніше.** Коли витягнеш commodity_Motive_Hunger і пов'язаний buff_Motive_Hunger_Starving — глянь на <L n="commodity_advertisements"> секцію commodity і <L n="loot_on_threshold_change"> (точна назва тегу може відрізнятись). Якщо threshold transitions виражаються через статичні entries в XML — pure tuning тягне. Якщо знаходиш посилання на core_services чи sim_state_runtime у Python supporting — запиши специфіку в patterns/commodity_threshold_patterns.md і ставимо question mark на gate.

**По Микиті mod stack** — він напевне дасть або через UI Mods Manager у грі (Mods → Game Options → Mod Manager), або через простий list вмісту папки Documents\Electronic Arts\The Sims 4\Mods з фільтром на .package і .ts4script. Без цього compatibility matrix буде гіпотетичною.

# Codex, по статусу

Прийняв новий scope. Vanilla DLC-style mod без runtime dependencies — правильна дизайн-цілка, особливо для першого релізу. Reach аудиторії при цьому ширше: базова гра безкоштовна, твій мод запрацює у будь-кого хто скачав Sims 4.

Декілька технічних наслідків які варто проговорити:

**1. Lot 51 Core Library як dependency справді відпадає.** Це означає що для injection-style операцій (додавання інтеракцій до існуючих об'єктів типу phone/computer) ти будеш писати свій injection шар з нуля. Це робиться через стандартні tuning механізми:

- _super_affordances injection через <L n="_super_affordances"> додавання у клон обʼєкта (не override)
- Або власний мінімальний .ts4script з простим pattern: services.affordance_manager().get(target_id).add_super_affordance(your_affordance)

Перевір на extracted XML як EA сама декларує super_affordances в object_phone_basic.xml або object_computer_basic.xml. Якщо вистачає tuning-only injection через додаткові tuning files які додають у списки — добре. Якщо EA вимагає overriding базового tuning (а не addition) — тоді або (а) приймаєте override з compatibility caveat, (б) робите свій script.

**2. Custom rabbit-hole без XML Injector.** XML Injector — це Scumbumbo's утиліта яка спрощує injection patterns. Без нього ти або робиш override базового tuning, або пишеш свій крихітний script. Реалістично для MVP — повний override непотрібен, можна обійтися:

- Self interactions (на сімі) — додаєш через trait's own _super_affordances список. Це чистий tuning, нічого не override-ить.
- Phone/computer interactions — складніше. Або власний мінімальний script (~30-50 рядків Python), або відкласти phone/computer integration на post-MVP.

Я б ставив на **MVP self-interactions only**, phone integration винести в Milestone 3-4. Це ще скорочує scope MVP без втрати корисності.

**3. Risk: tuning hash collisions і load order.** Без Lot 51 Core та інших libraries — ти єдиний хто пише tuning у своїй ніші. Менше ризику конфліктів, але також немає захисту від твоїх же помилок (типу випадкове перевикористання FNV64 hash). ids_registry.csv стає критично важливим, не просто корисним.

**4. Lot 51 Simdex як dev tool — підтримую.** Це браузер витягнутого tuning, ти його використовуєш на dev-машині, а не пакуєш у release. Для гравця це невидимо. Те саме для TDESC Browser.

**5. Reframing affordance to user.** "Жодних сторонніх runtime-залежностей" сильніше формулювання ніж просто "vanilla base game". Перше явне і вимірне (тест: скачав чисту базу + твій package = працює). Друге плутанне (можна сказати що "мод під vanilla" і потім вимагати XML Injector). Перше formulation я б використав у release notes.

# Питання до research phase

Поки не критичне, але корисне наперед: коли витягнеш superInteraction_Sim_GoJogging або еквівалент — звернути увагу на структуру **rabbit-hole exit**. EA рабіт-хол повертає сіма з outcome через loot_on_run або через окремий interaction_result. Pattern для self-initiated rabbit-hole interaction з probabilistic outcomes (як твоя "Піти шукати натхнення") має бути там. Якщо outcomes реалізовані через weighted_random_loot або random_outcome_loot — pure tuning тягне 100%. Якщо там Python виклик — ставимо ще одну question mark на gate.

# По Микиті

Mod stack справді не блокує MVP розробку. Compatibility матриця може бути роблена постфактум на release candidate (Milestone 7), не на старті.

Микита, тоді тобі поки тільки:

1. Виконати Extract All коли буде час за комп'ютером (~30 хв процесу + автоматична генерація хешів через простий PowerShell скрипт який Codex може дати)
2. Передати extracted XML у Codex для анотації

Список модів зараз не критичний. Збережи на момент коли підемо в compatibility smoke test — тоді скинеш Codex.

# Що далі

Codex, у тебе на твоєму боці зараз нема активних задач крім ще одної pre-extraction перевірки яку я б запропонував:

- Сформулювати **PowerShell snippet** для генерації SHA-256 manifest який Микита запустить після Extract All. Це 5 рядків, але фіксує форматування manifest CSV щоб не довелося потім переробляти. Зразок:
powershell
Get-ChildItem -Path .\research\extracted -Recurse -File | 
  ForEach-Object {
    $hash = (Get-FileHash $_.FullName -Algorithm SHA256).Hash
    "$($_.FullName.Replace((Resolve-Path .\research\extracted).Path + '\', ''))" + 
    ",$hash,$($_.Length),$(Get-Date -Format 'yyyy-MM-dd'),1.123.85.1020"
  } | Out-File -FilePath .\research\snapshot_manifest.csv -Append -Encoding utf8


Адаптуй під свій точний формат manifest колонок. Це автоматизує step "згенерувати hashes" з мого попереднього повідомлення.
